02

Model、Agent、Mode 到底差在哪？

這是新手最容易混在一起的四個層次。

1. Model = 大腦「誰在想？」

模型版本會變，不用死背型號。先理解：更強的模型通常適合複雜架構與除錯；更快的模型適合日常小修改。

2. Agent = 工程師「誰在做？」

Codex / Claude Code 不只是聊天介面，它們能讀 Repo、執行命令、修改檔案、測試與使用工具。

3. Mode = 工作方式「現在先想，還是直接做？」

Plan 類模式先調查與提出方案；執行類模式才真的修改程式。權限模式則決定每一步要不要先問你。

4. Rules = 公司規章「做事要遵守什麼？」

AGENTS.md / CLAUDE.md 放長期規則，例如語言、資料夾、測試方式與不能亂動的區域。

Claude Code

Plan Mode = 先勘查，不施工

Plan Mode 會讀檔、探索程式碼、提出方案，但在你批准前不改原始碼。很適合需求還沒完全想清楚，或改動範圍大的任務。

  • Sonnet：日常 coding 的平衡選擇。
  • Opus：複雜推理、架構與難題。
  • Haiku：較簡單、速度優先的工作。
  • opusplan：目前可讓 Plan 階段使用 Opus、執行階段切到 Sonnet。
Codex

Plan / Default = 規劃與執行分開

Codex 的 Plan collaboration mode 以非破壞性探索與完整計畫為主；切回 Default 後才執行修改。你也能選模型與 reasoning effort。

  • 較低 reasoning：快，適合明確的小修改。
  • 較高 reasoning：慢一些，但更適合跨檔、架構、難除錯。
  • 不要迷信最高：任務簡單時，高推理只會增加等待與成本。
超簡單比喻

Model 是工程師的腦袋；Codex / Claude Code 是你聘請的工程師；Plan Mode 是「先畫施工圖」；Default / Execute 是「開始施工」；AGENTS.md / CLAUDE.md 是公司 SOP。

04

每個工具到底負責什麼？

用最少的概念，把真正的開發世界串起來。

A

Git + GitHub：時光機 + 雲端總部

Git 負責版本；GitHub 放 Repo、Issue、Branch、PR。兩者不是同一個東西。

Git = 存檔系統　／　GitHub = 放存檔與協作的地方
B

GitHub Pages：把靜態網站公開

HTML / CSS / JavaScript 可以直接發布成公開網站。很適合第一個作品集，但它不會替你執行 Python、Node.js 或 SQLite 後端。

C

Notion：人看的文件

放需求、企劃、決策、旅遊規劃、TODO。它回答「為什麼做、想做什麼」。

D

README.md：Repo 的門面

告訴來到 GitHub 的人「這是什麼、怎麼執行、有哪些功能」。作品集一定要有。

E

AGENTS.md / CLAUDE.md：AI 的長期規則

不要每次重講「用繁中、不要改某資料夾、改完要測試」。把固定規則寫進專案。

F

Issue → Branch → Pull Request：正式的修改流程

Issue 是工單；Branch 是平行施工區；Pull Request 是「我改好了，請檢查後合併」。

G

Test：AI 說 Done 不代表真的 Done

至少檢查桌機、手機、舊功能、連結與部署。之後再學自動化測試。

H

.env / Secret：鑰匙不要貼在 GitHub 上

API Key、密碼、Token 不要 commit。公開 Repo 特別要養成這個習慣。

I

SQLite：Database 新手村

它可以把資料庫裝在一個檔案裡，很適合從「資料寫死在 HTML」進化到「程式讀資料」。

J

API：前台與資料之間的服務窗口

Frontend 不必直接碰 Database；它向 API 要資料，API 再處理資料庫與商業邏輯。

K

Connector / MCP：AI 與外部世界的橋

讓 AI 在你授權的範圍內使用 Gmail、Drive、Notion、GitHub、Database 等外部資料與工具，不用每次手動複製貼上。

L

Deploy + Log：上線與出事後找證據

Local 能跑不代表 Internet 能跑。Deploy 是把成品上線；Log 像飛機黑盒子，出錯時靠它查原因。

06

Python：不用背語法，先學會看懂

AI 可以負責寫大部分程式；你至少要能判斷它正在處理什麼資料、做什麼判斷，以及錯在哪裡。

AI 時代的 Python 目標

不是考你能不能從空白頁手寫程式，而是看到 Codex / Claude 產生的 Python 時，能大概讀懂、能問對問題、能看懂錯誤。

HTML = 內容 CSS = 長相 JavaScript = 瀏覽器互動 Python = 資料 / 自動化 / Backend 常見工具
變數city = "Tokyo"

替一個值取名字。

List["Tokyo", "Prague"]

一串資料。

Dictionary{"city": "Tokyo"}

有欄位名稱的一筆資料。

ifif days > 5:

符合條件才做事。

forfor trip in trips:

把一串資料逐筆處理。

functiondef total(...):

把一段工作包起來重複使用。

importimport json

使用現成工具或套件。

Error / TracebackKeyError: 'city'

程式留下的錯誤線索，不用靠猜。

你只要能讀懂這種程度

trips = [
    {"city": "Tokyo", "days": 5},
    {"city": "Prague", "days": 7}
]

for trip in trips:
    if trip["days"] > 5:
        print(trip["city"])

不用背，能翻成白話就夠

  1. trips 是一串旅行資料。
  2. for 把每趟旅行一個一個拿出來。
  3. if 判斷旅行是否超過 5 天。
  4. 符合條件就印出城市名稱。
看到不懂的語法 → 先叫 AI 解釋，不要急著叫它重寫整份。
比背語法更重要：遇到錯誤時，把「預期結果、實際結果、完整 Error / Traceback」交給 AI，先要求它解釋 root cause，再修改程式。

08

Connector：讓 AI 不只看得到聊天視窗

AI 本身很聰明，但如果沒有連接外部服務，它不知道你的信箱、雲端文件或工作系統裡有什麼。

🤖
沒有 Connector

AI 像待在房間裡的工程師，只能看你貼進來的文字與目前專案檔案。

授權的橋樑 →
✉️ Gmail 📁 Google Drive 📚 Notion 🐙 GitHub 🗄️ Database
產品裡常看到

Connector / App = 現成的門

例如把 Google Drive、Gmail 或 Notion 接到 AI。登入並授權後，AI 才能依照允許的權限搜尋、讀取，某些整合也能執行支援的動作。

重點：不是「AI 自動知道全部資料」，而是你先連線 + 授權。
Claude Code 常見

MCP = 通用的插座規格

Model Context Protocol 可以把 AI 接到外部工具、API、Database。你可以把 MCP 想成「USB-C 規格」：服務只要提供相容介面，AI 就知道怎麼使用它提供的工具。

Connector 是「一扇門」；MCP 是「大家可以遵循的門鎖規格」。
你下需求「整理下一趟旅行」
→
Codex / Claude / ChatGPT判斷需要哪些資料
→
Connector / MCP依權限呼叫工具
→
Gmail / Drive / Notion回傳需要的內容
→
完成任務整理、比較、更新或產生程式

沒有 Connector

你：我把機票 Email 貼給你。
你：這是住宿 PDF。
你：這是 Notion 行程。

AI：好，我來整理。

資料要自己找、自己複製、自己貼。

有 Connector

幫我找 Gmail 的機票確認信，
再看 Drive 的住宿資料與 Notion 行程，
整理出缺少預約的日期。

AI 可以直接向已授權的服務取得工作需要的資訊。

🔐 Authentication你是誰？先登入。
🎟️ Permission可以讀什麼、改什麼？
🎯 Scope只給完成任務需要的範圍。
✅ Confirmation寄信、刪檔等動作要特別小心。
最重要的安全觀念：Connector 不是把整個帳號「交給 AI」。AI 能做什麼取決於帳號本身的存取權、你授予的權限、工作區設定，以及該整合實際提供哪些操作。外部內容也可能包含惡意指令，所以高風險寫入動作不要無腦放行。
09

最適合新手的教學順序

不要從背語法開始。每一步都讓現有旅遊網站多一個「真的有用」的能力。

  1. 1

    把現有旅遊網站放進 GitHub

    建立 Repo、README，理解 Git 與 GitHub 的差異。

    成果：GitHub 上有第一個作品
  2. 2

    用 GitHub Pages 公開

    讓朋友用手機真的開得到。理解 Local → GitHub → Deploy → Internet。

    成果：一條公開網址
  3. 3

    建立 Notion 專案頁

    寫需求、TODO、旅行規劃，再把一個需求變成 GitHub Issue。

    成果：第一次有「需求 → 工單」
  4. 4

    加入 AGENTS.md / CLAUDE.md

    把 UI 語言、風格、禁區、測試規則交給 AI。

    成果：不用每次重講 SOP
  5. 5

    用 Plan Mode 做一次功能

    先分析、再批准、再實作。學會把「想」跟「做」拆開。

    成果：第一次有設計過的 AI 開發
  6. 6

    Branch → Test → Pull Request

    不要直接在正式版本施工。看 diff、驗證，再 merge。

    成果：接近公司的 Git 工作流
  7. 7

    10 分鐘讀懂 Python

    只學變數、List / Dictionary、if、for、function、import 與 Traceback 的概念；不用背語法。

    成果：AI 寫 Python 時你看得懂大意
  8. 8

    先理解 Connector / MCP

    不用先會串 API，只要理解「AI 如何在授權下連到 Gmail、Drive、Notion、GitHub 或其他工具」，並知道讀取與寫入權限不同。

    成果：知道 AI 如何跨系統工作
  9. 9

    SQLite → API → Backend

    等靜態網站真的遇到資料管理需求，再學 Database 與 Backend；不用一開始就把所有技術塞進來。

    成果：從網站走向 Web App

最後要學的不是「怎麼叫 AI 寫 Code」

而是能清楚告訴 AI：這是需求、這是現況、這是限制、這是規則；先分析方案，確認後實作，完成後驗證。

「幫我做一個網頁」→ 「先分析這個問題」→ 「這是需求與限制，先做 decision-complete plan，再實作與驗證。」
