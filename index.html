03

Git、GitHub 與正式修改流程

先理解用途，不需要先背一堆指令。

Git = 時光機

每一次提交（Commit）都像存檔點。真正重要的是能看差異（Diff）：這次到底改了什麼？

GitHub = 專案總部

放 Repo、工作單（Issue）、分支（Branch）、Pull Request（PR）、Actions、Pages，讓版本與協作集中在一起。

工具新手先這樣理解
工作單（Issue）這次要解決什麼？先把工作說清楚。
分支（Branch）平行施工區，不直接在正式版本亂改。
Pull Request（PR）改好了，先看差異（Diff）、檢查（Review），再合併。
合併（Merge）確認沒問題後放進 main。
GitHub Pages把靜態 HTML / CSS / JS 發布成公開網址。
 
工作單（Issue）→ 分支（Branch）→ 修改 → 測試（Test）
→ Pull Request（PR）→ 檢查（Review）→ 合併（Merge）→ main → 部署（Deploy）

測試（Test）：AI 說 Done 不代表真的 Done

  • 桌機版正常嗎？
  • 手機版正常嗎？
  • 舊功能還在嗎？
  • 連結、資料、日期正確嗎？
  • 部署後的公開網站也正常嗎？

.env / 機密資訊（Secret）

API Key、密碼、Token 不要提交（Commit）到 GitHub。.env.example 可以示範需要哪些環境變數，但不能放真正的機密資訊。

部署（Deploy）與日誌（Log）

部署是把本機成品真正上線；日誌是出錯後的證據。本機（Local）能跑，不代表公開網站一定能跑。

05

Python：目標是看得懂，不是默寫

AI 可以寫大部分語法，但你至少要能看出資料、條件、流程與錯誤大概在做什麼。

city = "Tokyo"變數：替資料取名字
["Hokkaido", "Tokyo", "Chiang Mai"]串列（List）：一串資料
{"city": "Tokyo"}字典（Dictionary）：有欄位名稱的資料
if days > 5:條件判斷（if）：符合條件才做
for trip in trips:迴圈（for）：逐筆處理
def total(...):函式（function）：把一段工作包起來
import json匯入（import）：使用現成工具
KeyError: 'city'錯誤追蹤（Traceback）：找錯誤線索
trips = [
    {"city": "Hokkaido", "days": 7},
    {"city": "Tokyo", "days": 5},
    {"city": "Chiang Mai", "days": 4}
]

for trip in trips:
    if trip["days"] > 5:
        print(trip["city"])

只要能翻成白話：「把每趟旅行拿出來，找超過五天的，再印出城市」就已經達到這裡的目標。

比背語法更重要：看錯誤與錯誤追蹤（Error / Traceback）

遇到錯誤時，把「預期結果、實際結果、完整 Error」交給 AI，先要求它解釋根本原因（root cause），再修改。

預期（Expected）：
GET /api/trips 應該回傳旅行資料。

實際（Actual）：
HTTP 500 / KeyError: 'city'

請先解釋根本原因（root cause），不要直接改 code。
再告訴我最小修改方案。

07

連接器（Connector）、MCP 與外部系統

讓 AI 能在授權範圍內使用外部服務，而不是每次都靠你複製貼上。

沒有連接器（Connector）
AI ← 你手動貼 Email / PDF / Notion

有連接器（Connector）
AI → 授權的工具 → Gmail / Drive / Notion / GitHub
連接器（Connector / App）
產品提供的現成整合。登入並授權後，AI 才能使用整合實際提供的資料與操作。
MCP
讓 AI 工具連接外部服務的一種通用協定，可以把它理解成共同的「工具插座規格」。
身分驗證（Authentication）
先確認「你是誰」。
權限（Permission）
決定「可以讀什麼、可以改什麼」。
權限範圍（Scope）
只給完成任務真正需要的範圍。
操作確認（Confirmation）
寄信、刪檔、公開發布等寫入動作要特別確認。

我把機票 Email 貼給你。

找 Gmail 的機票確認信，

你下需求
   ↓
Codex / Claude / ChatGPT
   ↓

   ↓
Gmail · Drive · Notion · GitHub · 資料庫
   ↓
整理 / 比較 / 更新 / 產生程式
連接器不是把整個帳號交給 AI。AI 能做什麼取決於帳號本身存取權、你授予的權限、工作區設定，以及該整合實際支援哪些操作。

先規劃（Plan）

我要新增 Chiang Mai 行程。
先不要修改任何檔案。

請先：
1. 看目前專案結構
2. 找出需要修改哪些檔案
3. 說明資料應該放哪裡
4. 說明可能影響哪些既有功能
5. 提出實作與測試計畫

再執行（Execute）

依照剛才的計畫實作。

限制：
- 保留現有功能
- UI 使用繁體中文
- 手機版不能壞
- 完成後自行測試
- 最後摘要修改檔案與結果
AI 不只是替你打字。好的 AI Coding 是：讓 AI 先理解現況與限制，再實作；你負責判斷方向、檢查差異（Review diff）、驗證結果。

10

建議學習順序

用同一個專案一路往下，不要拆成十個互不相關的小練習。

  1. 01
    GitHub + GitHub Pages

    先知道程式放在哪裡、版本怎麼保存、網站怎麼公開。

  2. 02
    README + 專案架構

    學會看 Repo，不只看最後畫面。

  3. 03
    Notion + AGENTS.md / CLAUDE.md

    把需求、人看的文件與 AI 規則分開。

  4. 04
    規劃 → 分支 → 實作 → 測試 → PR

    建立真正的 AI Coding 工作方式。

  5. 05
    Python 概念

    讀得懂 AI 寫的基本程式與錯誤追蹤（Traceback）。

  6. 06
    連接器（Connector）/ MCP

    理解 AI 如何在授權下跨系統工作。

  7. 07
    Google Cloud + Gmail / Drive 實作

    真的完成一個有權限、有後端、有部署的 Web App。

  8. 08
    SQLite → API → 後端（Backend）

    等真的需要動態資料時，再進下一層。

  9. 09
    擴充同一個作品

    Trip Card、Calendar、AI Summary，而不是重新做另一個無關 Demo。

最後要學的不是「怎麼叫 AI 寫 Code」。 而是能清楚告訴 AI：這是需求、這是現況、這是限制、這是規則；先分析方案，確認後實作，完成後驗證。
