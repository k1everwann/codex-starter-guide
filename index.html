01

AI 模型、Agent 與模式

先把 Model、Agent、Mode、Rules 四個最容易混在一起的概念拆開。

Model
誰在想。 模型是大腦。較強的模型通常適合複雜架構、跨檔分析與難除錯；較快的模型適合明確的小修改。
Agent
誰在做。 Codex / Claude Code 能讀 Repo、改檔案、執行工具、測試，而不只是聊天。
Mode
現在怎麼工作。 Plan 類模式先調查與規劃；Default / Execute 類模式才真正改程式。
Rules
做事要遵守什麼。 固定規則可以放在 AGENTS.md 或 CLAUDE.md，避免每次重講。

Claude：先理解模型取向

概念新手先這樣理解
Sonnet日常 coding 的平衡選擇，速度與能力兼顧。
Opus複雜推理、架構與難題，適合先做較深的分析。
Haiku較簡單、速度優先的工作。
Plan Mode先讀檔、探索、提出方案，不先動原始碼。
opusplan可以理解成：規劃階段用較強推理，執行時再切回較快模型。

Codex：Plan、Default 與 reasoning

設定適合情況
較低 reasoning明確的小修改、速度優先。
較高 reasoning跨檔、架構、複雜 bug、需要先理解整個專案。
Plan先做非破壞性探索，產出完整計畫。
Default / Execute確認方案後才進入實作。
 
Model   = 工程師的大腦
Agent   = 工程師本人
Plan    = 先看圖、量尺寸
Execute = 開始施工
Rules   = 公司 SOP
不要迷信全部開最高。任務很簡單時，高推理只會增加時間與成本。真正要學的是：什麼時候應該先 Plan，什麼時候可以直接做。

03

Git、GitHub 與正式修改流程

先理解用途，不需要先背一堆指令。

Git = 時光機

每一次 commit 都像存檔點。真正重要的是能看 diff：這次到底改了什麼？

GitHub = 專案總部

放 Repo、Issue、Branch、Pull Request、Actions、Pages，讓版本與協作集中在一起。

工具新手先這樣理解
Issue工作單：這次要解決什麼？
Branch平行施工區，不直接在正式版本亂改。
Pull Request改好了，先看 diff、Review，再合併。
Merge確認沒問題後放進 main。
GitHub Pages把靜態 HTML / CSS / JS 發布成公開網址。
 
Issue → Branch → 修改 → Test → Pull Request → Review → Merge → main → Deploy

Test：AI 說 Done 不代表真的 Done

  • 桌機版正常嗎？
  • 手機版正常嗎？
  • 舊功能還在嗎？
  • 連結、資料、日期正確嗎？
  • 部署後的公開網站也正常嗎？

.env / Secret

API Key、密碼、Token 不要 commit 到 GitHub。.env.example 可以示範需要哪些環境變數，但不能放真正的秘密。

Deploy 與 Log

Deploy 是把本機成品真正上線；Log 是出錯後的證據。Local 能跑，不代表 Internet 一定能跑。

05

Python：目標是看得懂，不是默寫

AI 可以寫大部分語法，但你至少要能看出資料、條件、流程與錯誤大概在做什麼。

city = "Tokyo"變數：替資料取名字
["Tokyo", "Prague"]List：一串資料
{"city": "Tokyo"}Dictionary：有欄位名稱的資料
if days > 5:if：條件判斷
for trip in trips:for：逐筆處理
def total(...):function：把工作包起來
import jsonimport：使用現成工具
KeyError: 'city'Traceback：錯誤線索
trips = [
    {"city": "Tokyo", "days": 5},
    {"city": "Prague", "days": 7}
]

for trip in trips:
    if trip["days"] > 5:
        print(trip["city"])

只要能翻成白話：「把每趟旅行拿出來，找超過五天的，再印出城市」就已經達到這裡的目標。

比背語法更重要：看 Error / Traceback

遇到錯誤時，把「預期結果、實際結果、完整 Error」交給 AI，先要求它解釋 root cause，再修改。

Expected:
GET /api/trips 應該回傳旅行資料。

Actual:
HTTP 500 / KeyError: 'city'

請先解釋 root cause，不要直接改 code。
再告訴我最小修改方案。

07

Connector、MCP 與外部系統

讓 AI 能在授權範圍內使用外部服務，而不是每次都靠你複製貼上。

沒有 Connector
AI ← 你手動貼 Email / PDF / Notion

有 Connector
AI → 授權的工具 → Gmail / Drive / Notion / GitHub
Connector / App
產品提供的現成整合。登入並授權後，AI 才能使用整合實際提供的資料與操作。
MCP
讓 AI 工具連接外部服務的一種通用協定，可以把它理解成共同的「工具插座規格」。
Authentication
先確認「你是誰」。
Permission
決定「可以讀什麼、可以改什麼」。
Scope
只給完成任務真正需要的範圍。
Confirmation
寄信、刪檔、公開發布等寫入動作要特別確認。

旅遊例子

沒有 Connector

我把機票 Email 貼給你。
這是住宿 PDF。
這是 Notion 行程。
請幫我整理。

有 Connector

找 Gmail 的機票確認信，
再看 Drive 的住宿資料與 Notion 行程，

Connector 不是把整個帳號交給 AI。AI 能做什麼取決於帳號本身存取權、你授予的權限、工作區設定，以及該整合實際支援哪些操作。

先 Plan

我要新增 Prague 行程。
先不要修改任何檔案。

請先：
1. 看目前專案結構
2. 找出需要修改哪些檔案
3. 說明資料應該放哪裡
4. 說明可能影響哪些既有功能
5. 提出實作與測試計畫

再 Execute

依照剛才的計畫實作。

限制：
- 保留現有功能
- UI 使用繁體中文
- 手機版不能壞
- 完成後自行測試
- 最後摘要修改檔案與結果
AI 不只是替你打字。好的 AI Coding 是：讓 AI 先理解現況與限制，再實作；你負責判斷方向、Review diff、驗證結果。

建議學習順序

用同一個專案一路往下，不要拆成十個互不相關的小練習。

  1. 01
    GitHub + GitHub Pages

    先知道程式放在哪裡、版本怎麼保存、網站怎麼公開。

  2. 02
    README + 專案架構

    學會看 Repo，不只看最後畫面。

  3. 03
    Notion + AGENTS.md / CLAUDE.md

    把需求、人看的文件與 AI 規則分開。

  4. 04
    Plan → Branch → Execute → Test → PR

    建立真正的 AI Coding 工作方式。

  5. 05
    Python 概念

    讀得懂 AI 寫的基本程式與 Traceback。

  6. 06
    Connector / MCP

    理解 AI 如何在授權下跨系統工作。

  7. 07
    GCP + Gmail / Drive Hands-on

    真的完成一個有權限、有 Backend、有 Deploy 的 Web App。

  8. 08
    SQLite → API → Backend

    等真的需要動態資料時，再進下一層。

  9. 09
    擴充同一個作品

    Trip Card、Calendar、AI Summary，而不是重新做另一個無關 Demo。

最後要學的不是「怎麼叫 AI 寫 Code」。 而是能清楚告訴 AI：這是需求、這是現況、這是限制、這是規則；先分析方案，確認後實作，完成後驗證。
